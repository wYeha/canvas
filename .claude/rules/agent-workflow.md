# Порядок работы агента (для любого ИИ-агента: Claude Code, Cursor и др.)

Этот файл собирает в одном месте всё, что раньше жило вне репозитория: договорённости с пользователем, порядок работы и уроки прошлых итераций. Читать **до** любой правки вместе с:

1. [CLAUDE.md](../../CLAUDE.md) — краткие инструкции (строки `@docs/...` там — импорты: эти файлы нужно открыть и прочитать самому);
2. [docs/rules/frontend.md](../../docs/rules/frontend.md) — **обязательные** правила фронтенда, прочитать целиком;
3. [docs/rules/backend.md](../../docs/rules/backend.md) — правила бэкенда (этап 10, пока не нужен);
4. [docs/PLAN.md](../../docs/PLAN.md) — чеклист итераций; заметки `> ...` под готовыми пунктами описывают реальные решения и отклонения — читать заметки своего этапа и смежных;
5. [docs/DESIGN.md](../../docs/DESIGN.md) и [docs/TOKENS.md](../../docs/TOKENS.md) — дизайн-решения и значения;
6. [docs/USER_GUIDE.md](../../docs/USER_GUIDE.md) — руководство пользователя.

Если правило мешает задаче — остановиться и спросить пользователя, не обходить молча.

## Договорённости с пользователем

- Общение, комментарии в коде, коммиты — на русском.
- Одна итерация `X.Y` из PLAN.md за раз, по порядку. Делать только её, не забегать вперёд.
- **После каждой завершённой итерации — коммит в `main`. Push запрещён.** В конце коммита строка `Co-Authored-By: <модель> <noreply@...>` — по желанию, не обязательно.
- **Деплой и этап 10 (бэкенд) не начинать**, пока пользователь явно не скажет.
- Не предлагать заново React, Tailwind, экспорт в JSON — решения приняты (Vue 3 + TS + Pinia + SCSS/BEM, экспорт — HTML с инлайн-стилями).
- Скиллы/воркфлоу `superpowers:*` не использовать никогда.

## Главный продуктовый принцип

Инструмент нужен, чтобы ИИ-агент по экспортированному HTML понял структуру и вложенность макета, а **не для визуального дизайна**. Каждая настройка UI либо меняет экспорт (flex/grid, padding, размеры, подписи, теги, связи), либо помогает человеку читать структуру на канвасе. Декоративных настроек не добавлять (цвет блока — только автоматически по глубине, вручную не задаётся и не экспортируется). Нет понятия «фрейм» — есть только блоки; блок прямо на поле — корневой, у него ширина превью. Панели фиксированные: не скрываются, не сворачиваются, не меняют размер, не двигаются.

## Готовность итерации (definition of done)

1. `npm run check` из корня зелёный (Prettier, Stylelint, vue-tsc, ESLint, Vitest). Сначала `npm run format`, потом `npm run check`.
2. У каждого нового файла — шапка-комментарий, у каждой функции (включая функции внутри composable, экшены стора, **и функции, возвращаемые из composable** — ESLint требует JSDoc и у них; стрелочные функции в объекте `return` без JSDoc валят линт, делайте именованные `function`) — JSDoc на русском.
3. Чистая логика — в отдельных `.ts` без Vue/Pinia, покрыта тестами Vitest в `__tests__/`. Для фрагментов с поведением — DOM-тесты (`*.dom.test.ts`, `@vue/test-utils`, см. `canvas-layers.dom.test.ts`).
4. [docs/USER_GUIDE.md](../../docs/USER_GUIDE.md) описывает каждое новое/изменённое действие (что нажать, куда смотреть), новые горячие клавиши — в таблице, готовые разделы помечены ✅, упоминания «появится позже» для сделанного убраны.
5. В PLAN.md пункт отмечен `[x]`, под ним заметка `  > ...`: какие файлы/функции, ключевые решения, отклонения от плана, проверено ли в браузере.
6. Новые значения размеров — сначала в TOKENS.md, затем в `_variables.scss`; новые цвета — в обе темы.
7. Коммит: `X.Y: короткое описание`.

## Схема работы по сложности

- **Простые итерации** (вёрстка, стили, мелкие правки): сразу реализовать.
- **Сложная логика** (этап 7 перетаскивание, этап 8 связи — все пункты): сначала план в `.claude/plans/YYYY-MM-DD-HH-MM-<название>.md` — цель и контекст, декомпозиция чеклистом, риски и митигации, архитектурные решения, затронутые файлы. Затем реализация по плану, затем **саморевью** (см. ниже) сразу после итерации, исправления, коммит.
- **В конце каждого этапа** — ревью общего diff этапа (`git diff <последний коммит до этапа>..HEAD`), правки отдельным коммитом `Этап N: правки по ревью`, итоговая заметка `> Ревью этапа N: ...` после последнего пункта этапа в PLAN.md.

### Чеклист ревью

- Корректность: гонки фокуса/`blur`, взаимодействие с глобальными хоткеями, сброс ховера/выделения, удаление узла во время действия, undo/redo во время действия, утечки слушателей (снимаются в `onBeforeUnmount`).
- Правила раздела 11 frontend.md, проверяемые только на ревью: функции ≤ ~40 строк, нет магических чисел/строк (всё в `constants.ts`), `:key` по id, чистая логика без Vue, классы через computed, `Ui*` без стора, DOM только в `scripts/` (`node-dom.ts` и т. п.).
- Производительность: на больших документах не пересчитывать всё дерево на каждое движение мыши — дробить computed (булевы computed не будят зависимых, если значение не изменилось).
- Доступность: aria-атрибуты, клавиатура.

## Уроки прошлых итераций (неочевидное в коде)

- **Фокус.** Кнопки панелей вешают `@mousedown="keepFocusOnMouseDown"` (`scripts/globals/focus.ts`): иначе кнопка держит фокус и пробел жмёт её вместо пана поля. Следствие: клик по такой кнопке **не вызывает `blur`** у открытого поля ввода — открытый ввод нужно завершать явно (`labelEdit.finish()`) в обработчиках кликов.
- **Хоткеи** (`use-canvas-hotkeys.ts`) глобальные, на window; не срабатывают в полях ввода, при открытом окне экспорта и пока открыт ввод подписи (`labelEdit.editingId !== null`). Любое состояние, где `editingId` выставлен, а поля в DOM нет, блокирует все хоткеи — не допускать.
- **Ховер** — один `pointermove` на viewport в `use-canvas-select.ts`: на поле — по `data-node-id`, над строкой «Слоёв» — по `data-layer-id`. Не вешать ховер-обработчики в самих строках: обработчик viewport их перебьёт.
- **Подписи на канвасе** (чип, подпись листа) имеют `pointer-events: none` — клик проходит в блок; попадание в подпись проверяется геометрически (`labelNodeIdAt` в `node-dom.ts`).
- **`:style` разрешён только** для исключений из frontend.md §4.4 (раскладка блоков через `node-style.ts`, камера через `camera-style.ts`, позиция корня `rootPlacementStyle`, оверлей `overlayRectStyle`, всплывающие списки `popupStyle`, индикаторы перетаскивания — `dnd/dnd-style.ts`: `dragGhostStyle` и будущие линия вставки / рамка приёмника там же). Иное новое динамическое позиционирование — добавлять такой же функцией в `scripts/` и дописывать исключение в frontend.md §4.4, согласовав с пользователем.
- **Перетаскивание** (этап 7): стор `dnd/drag-store.ts` (`session`, `draggingId`, `isDragging`), события — `dnd/use-canvas-dnd.ts` (подключён в `use-canvas-viewport.ts` после выделения). Pointer capture берётся только после порога 4px (иначе `pointerup` клика уходит во viewport и снимает выделение). Пока идёт перетаскивание, хоткеи канваса заблокированы, `Esc` ловится в capture-фазе на window. Геометрия — чистые функции `dnd/dnd-geometry.ts` (захват в координатах поля, призрак — по текущему зуму). Сессия — объединение по `kind`: `node` (призрак, `draggingId`) и `root` (корень за заголовок `data-root-handle-id`, предпросмотр `rootPosition` без записи в документ, запись одним `moveNode` при отпускании, `movingRootId`).
- **Камера**: координаты поля ↔ экран — `camera.ts` (`worldToScreen`, `screenToWorld`, `toWorldRect`); зум учитывать везде. Видимая область без панелей — `cameraStore.visibleArea` (`CANVAS_SAFE_INSETS`).
- **История**: каждое действие — один `commit` в `layout-store.ts`; склейка по ключу (`MergeOptions`), без транзакций. Операции над деревом — чистые, не мутируют вход (`tree.ts`, `tree-move.ts`: `moveNode`, `MoveTarget`).
- **Стор ввода подписи** `label-edit-store.ts`: режимы `create`/`rename`, место `canvas`/`layers`, `layersPickId` (F2 после клика по строке слоя открывает поле в строке).
- **Состояние только одной панели** (например, свёрнутые ветки «Слоёв») — не в Pinia, а в composable панели + provide/inject.
- **Визуальная проверка**: `npm run dev` (порт 5173), демо-документ — `http://localhost:5173/?demo` (только dev, не сохраняется), витрина компонентов — `?ui`. После UI-итерации проверить в браузере обе темы, если меняли оформление.
- **Windows**: в репозитории `core.autocrlf=true`; Prettier следит за форматом — после правок запускать `npm run format`.
